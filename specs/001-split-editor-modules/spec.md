# 기능 명세: 편집기 모듈 분리

**작성일**: 2026-10-22
**상태**: 명확화 완료
**입력**: 하나의 플러그인으로 배포하면서 queryeditor와 modeleditor를 모듈로 분리한다. 각 모듈은 glue_sql과 glue_uml_ad 확장자를 처리한다.

## 명확화

### 2026-10-22

- 질문: 두 모듈을 하나의 플러그인으로 배포하는가? 답변: 하나로 묶어 배포하되 모듈로 분리한다.
- 확정 사항: queryeditor는 glue_sql, modeleditor는 glue_uml_ad를 담당한다.

### 멀티뷰 확장 명확화

- 사용자 추가 요구: 두 모듈 모두 Design과 Source 탭을 제공하며 Source는 XML 편집기로 동작한다.
- 현재 범위: queryeditor의 Design은 queryMap 목록·속성·SQL 편집을 제공한다. modeleditor의 Design은 기본 안내 화면을 유지한다.
- 탭 순서는 Design, Source이며 최초 열기에서는 Design을 기본으로 사용한다. 이후 선택과 편집 위치 복원은 IDE의 기본 동작을 따른다.

### 쿼리 Design 확장 명확화

- 기준 파일은 사용자가 지정한 queryeditor/sample-query.glue_sql이다.
- 왼쪽은 문법 기능을 추가하지 않은 다중 행 SQL 편집기이고, 오른쪽은 queryMap desc 입력·쿼리 속성 입력·query.id 목록 순서다.
- 최상단 desc 입력은 queryMap 설명이며 쿼리 속성의 desc는 선택한 query 설명이다. isNamed는 참/거짓 체크박스로 제공한다.
- 최초 쿼리를 기본 선택하며 변경은 공통 Source 문서에 반영한다. 쿼리 추가·삭제·실행과 SQL 문법 기능은 이번 범위 밖이다.
- 누락·중복 id도 행을 잃지 않고 표시한다. 잘못된 XML과 지원하지 않는 중첩 쿼리 본문은 Source 수정을 안내하고 Design에서 덮어쓰지 않는다.

## 사용자 시나리오 및 검증

### 사용자 이야기 1 — 모듈별 개발과 통합 배포 (우선순위: P1)

개발자는 각 편집기의 코드와 리소스를 별도로 관리하고 사용자는 한 번 설치하여 두 기능을 사용한다.

**독립 검증**: 두 모듈을 각각 컴파일하고 통합 배포물에 두 모듈의 클래스와 등록 정보가 포함되는지 확인한다.

**인수 시나리오**:

1. 두 편집기 모듈은 각각 자신의 소스 및 리소스 디렉터리를 갖는다.
2. 루트에서 배포물을 생성하면 기존 플러그인 식별자를 유지하는 단일 설치 파일이 만들어진다.
3. 한 편집기 모듈이 다른 편집기 모듈에 의존하지 않는다.

### 사용자 이야기 2 — 확장자별 파일 인식 (우선순위: P1)

사용자는 지정된 확장자의 파일을 열고 텍스트를 편집하고 저장할 수 있다.

**독립 검증**: 각 확장자의 파일이 담당 모듈의 파일 형식으로 판별되는지 플랫폼 테스트로 확인한다.

**인수 시나리오**:

1. example.glue_sql은 queryeditor가 제공하는 파일 형식으로 열린다.
2. example.glue_uml_ad는 modeleditor가 제공하는 파일 형식으로 열린다.
3. 두 형식 모두 기본 텍스트 편집과 저장을 지원한다.

### 사용자 이야기 3 — 두 편집기의 멀티뷰 (우선순위: P1)

사용자는 두 확장자의 파일을 열어 Design과 Source 탭 사이를 전환한다.

**독립 검증**: 각 파일의 편집기에 Design과 Source가 정확히 하나씩 표시되고 일반 텍스트 탭이 중복되지 않는지 확인한다.

**인수 시나리오**:

1. glue_sql과 glue_uml_ad를 각각 열면 Design, Source 순서로 두 탭이 나타난다.
2. queryeditor의 Design에는 쿼리 편집 화면이, modeleditor에는 안내 화면이 나타난다. 단순 표시와 탭 전환은 파일 내용을 변경하지 않는다.
3. Source에서 변경한 내용을 저장하지 않고 탭을 전환한 뒤 돌아와도 내용이 유지된다.

### 사용자 이야기 4 — XML 소스 편집 (우선순위: P1)

사용자는 Source에서 XML 구문 강조, 구문 오류 표시, 태그 완성 및 서식 정리를 사용하고 원래 확장자로 저장한다.

**독립 검증**: 두 형식 모두 XML 문서로 인식되는지 확인하고 Source에서 편집·실행 취소·다시 실행·저장을 검증한다.

**인수 시나리오**:

1. 각 파일의 XML 태그가 강조되고 잘못 닫힌 태그는 오류로 표시된다.
2. 태그 완성과 서식 정리가 동작한다. 사용자 스키마가 없는 태그·속성의 의미 기반 추천은 보장하지 않는다.
3. 편집·저장·재열기 후 내용과 원래 확장자가 유지된다.

### 사용자 이야기 5 — 쿼리 조회 및 선택 (우선순위: P1)

사용자는 queryMap을 열어 오른쪽 설명과 id 목록을 보고 쿼리를 선택한다. 선택할 때마다 왼쪽 SQL과 오른쪽 속성이 해당 쿼리 내용으로 바뀐다.

**독립 검증**: 제공된 샘플의 모든 쿼리가 문서 순서로 표시되고 각 선택에 SQL과 속성이 일치하는지 확인한다.

**인수 시나리오**:

1. queryMap desc가 속성 입력 위에 표시되고 그 아래에 id, desc, resultType, isNamed와 쿼리 목록이 나타난다.
2. 첫 쿼리가 기본 선택되고 목록 선택에 따라 SQL과 네 속성이 함께 바뀐다.
3. 빈 목록과 누락·중복 id가 있어도 잘못된 쿼리를 선택하거나 다른 쿼리를 덮어쓰지 않는다.

### 사용자 이야기 6 — 쿼리 SQL 및 속성 수정 (우선순위: P1)

사용자는 왼쪽 편집기와 오른쪽 입력으로 선택한 쿼리를 수정하고 Source에서 같은 변경을 확인한다.

**독립 검증**: SQL과 네 속성을 수정한 후 Source 문서 및 저장 파일을 확인하고 다른 쿼리와 주석·네임스페이스가 유지되는지 확인한다.

**인수 시나리오**:

1. SQL은 CDATA 마커 없이 표시되고 다중 행 텍스트로 수정할 수 있다. SQL 문법 강조·검사·실행은 제공하지 않는다.
2. id, desc, resultType 및 isNamed의 변경이 선택 쿼리의 속성에 반영되고 id 변경은 목록에도 반영된다.
3. Source 수정 및 실행 취소·다시 실행 후 Design을 다시 표시하면 변경된 목록·속성·SQL이 반영된다.
4. 특수문자와 CDATA 종료 문자열도 XML을 깨뜨리지 않고 저장하며 다른 쿼리와 문서의 불필요한 재작성은 하지 않는다.

### 사용자 이야기 7 — 패널 너비 조절 (우선순위: P2)

사용자는 왼쪽 SQL과 오른쪽 속성·목록 사이의 구분선을 끌어 오른쪽 너비를 조절한다.

**독립 검증**: 기본 너비와 최소 너비를 확인하고 구분선 이동으로 두 영역의 너비가 바뀌는지 확인한다.

**인수 시나리오**:

1. 오른쪽 영역은 일반 편집 창에서 약 320픽셀을 초기 기준으로 사용하며 최소 220픽셀을 확보한다.
2. 창 크기에 맞춰 SQL과 오른쪽 영역이 늘어나고 사용자가 구분선을 이동할 수 있다.

### 경계 조건

- 빈 파일도 해당 파일 형식으로 인식한다.
- 일반 sql, uml, txt 확장자의 기존 연결을 가로채지 않는다.
- 기존 샘플 도구 창은 분리 후에도 유지한다.
- 빈 XML이나 잘못된 XML도 Source에서 열어 수정할 수 있다.
- 읽기 전용 파일은 Source에서도 쓰기 제한을 유지한다.
- 일반 xml 파일에 전용 Design/Source 탭을 추가하지 않는다.
- Source의 편집 문서는 하나이며 탭 전환이나 Design 표시 과정에서 XML 내용을 다시 쓰지 않는다. 명시적인 쿼리 Design 편집은 해당 queryMap 설명 또는 선택한 쿼리만 갱신한다.
- 빈 문서, 잘못된 XML, queryMap이 아닌 루트는 안내를 표시하고 Design 입력을 비활성화한다.
- 읽기 전용 파일의 Design도 수정을 제한한다.
- query 본문에 하위 태그나 주석이 있으면 목록과 속성은 읽되 SQL 본문을 덮어쓰지 않고 Source 편집을 안내한다.

## 요구사항

- **FR-001**: queryeditor와 modeleditor의 소스 및 리소스를 분리하여 관리해야 한다.
- **FR-002**: 두 모듈은 하나의 플러그인으로 설치되어야 하며 기존 식별자를 유지해야 한다.
- **FR-003**: queryeditor가 glue_sql 파일의 인식과 기본 텍스트 편집을 담당해야 한다.
- **FR-004**: modeleditor가 glue_uml_ad 파일의 인식과 기본 텍스트 편집을 담당해야 한다.
- **FR-005**: 두 모듈 간 직접 의존성이 없어야 하며 다른 확장자의 처리를 변경하지 않아야 한다.
- **FR-006**: 기존 샘플 도구 창을 유지하고 개발 및 검증 방법을 문서화해야 한다.
- **FR-007**: 두 확장자의 파일 모두 Design, Source 순서의 멀티뷰를 제공해야 한다.
- **FR-008**: 기본 텍스트 편집기 탭을 중복 표시하지 않아야 한다.
- **FR-009**: Source는 XML 인식, 구문 강조, 구문 검사, 태그 완성 및 서식 정리를 제공해야 한다.
- **FR-010**: queryeditor Design은 쿼리 편집 화면을 제공하고 modeleditor Design은 안내 화면을 유지해야 한다. 단순 표시와 탭 전환은 파일을 변경하지 않아야 한다.
- **FR-011**: Source의 편집·저장·실행 취소·다시 실행과 탭 전환 시 미저장 문서 및 원래 확장자를 유지해야 한다.
- **FR-012**: 빈 파일·잘못된 XML·읽기 전용 파일을 IDE 기본 동작에 따라 처리해야 한다.
- **FR-013**: 일반 xml 파일이나 상대 모듈의 확장자에는 각 모듈의 멀티뷰를 적용하지 않아야 한다.
- **FR-014**: queryMap의 직접 자식 query를 문서 순서대로 query.id 목록으로 표시해야 한다.
- **FR-015**: queryMap desc를 오른쪽 최상단에 표시하고 그 아래에 선택한 query의 id, desc, resultType 및 isNamed 수정 입력을 제공해야 한다.
- **FR-016**: 쿼리 선택 시 왼쪽 SQL과 네 속성을 함께 갱신하고 최초에는 첫 쿼리를 선택해야 한다.
- **FR-017**: 왼쪽에 문법 기능을 추가하지 않은 다중 행 SQL 편집기를 제공하고 선택 쿼리의 본문을 수정할 수 있어야 한다.
- **FR-018**: 속성과 SQL 변경은 Source와 같은 문서에 반영하고 id 변경 시 목록과 선택을 유지해야 한다.
- **FR-019**: Source 수정과 실행 취소·다시 실행을 Design에 반영하고 선택 변경이나 동기화로 데이터를 잃지 않아야 한다.
- **FR-020**: 네임스페이스, 다른 쿼리, 속성 및 주석을 보존하고 XML 특수문자 및 CDATA 종료 문자열을 안전하게 처리해야 한다.
- **FR-021**: 오른쪽 영역은 초기 약 320픽셀, 최소 220픽셀을 기준으로 하며 사용자가 구분선을 끌어 크기를 조절할 수 있어야 한다.
- **FR-022**: 빈 목록·누락/중복 id·잘못된 XML·읽기 전용 파일을 안전하게 처리하고 지원하지 않는 중첩 본문을 덮어쓰지 않아야 한다.
- **FR-023**: 편집기 해제 시 SQL 편집기와 문서 리스너·예약 갱신 작업을 함께 해제해야 한다.

## 성공 기준

- **SC-001**: 두 모듈의 개별 컴파일이 모두 성공한다.
- **SC-002**: 하나의 설치 파일에 두 편집기의 클래스와 등록 정보가 모두 포함된다.
- **SC-003**: 두 지정 확장자와 세 비대상 확장자의 파일 형식 판별 검증이 모두 통과한다.
- **SC-004**: 두 대상 확장자에서 Design과 Source가 각각 하나씩 나타나며 다른 확장자에는 적용되지 않는다.
- **SC-005**: 두 형식이 모두 XML로 분석되고 구문 강조·오류 탐지·태그 완성·서식 정리 검증을 통과한다.
- **SC-006**: 두 형식에서 편집·탭 전환·실행 취소·다시 실행·저장 시나리오의 데이터 손실이 없다.
- **SC-007**: 기준 샘플의 모든 query를 선택했을 때 id 목록·네 속성·SQL이 원문과 일치한다.
- **SC-008**: SQL 및 네 속성 수정, Source 반영, 실행 취소·다시 실행 및 저장 검증이 모두 통과한다.
- **SC-009**: 특수문자·CDATA 종료 문자열·중복 id·빈 목록·잘못된 XML·읽기 전용 및 중첩 본문 검증에서 문서 손상이 없다.
- **SC-010**: 오른쪽 기본·최소 너비와 사용자 크기 조절 검증이 통과한다.

## 가정 및 범위

- 현재 분리된 두 모듈과 Design/Source 멀티뷰 기반을 확장한다.
- 쿼리 실행, SQL 구문 분석, UML 시각 편집 및 별도 저장 형식 설계는 이번 범위에 포함하지 않는다.
- 두 파일 형식은 IntelliJ XML Source를 사용한다. queryeditor Design은 queryMap 편집을, modeleditor Design은 기본 안내를 제공한다.
- XML에 선언된 스키마나 IDE에 등록된 스키마가 있으면 해당 범위의 XML 검증과 추천을 사용한다. 전용 스키마는 이번 범위에 추가하지 않는다.

## 사용자 이야기 8 — 설명 편집과 화면 정리 (우선순위: P1)

사용자는 queryMap 설명을 수정하고 resultType 오른쪽에서 isNamed를 조작한다. 하단에 쿼리 개수는 표시하지 않는다.

**독립 검증 및 인수 시나리오**:

1. queryMap desc를 수정·비우기·저장하고 Source 수정 및 실행 취소·다시 실행을 입력에 반영한다. 특수문자와 다른 쿼리·속성·주석·네임스페이스 및 선택을 보존한다.
2. 쿼리나 desc가 없어도 정상 XML의 설명은 편집 가능하고 잘못된 XML·읽기 전용에서는 비활성화한다.
3. isNamed가 resultType과 같은 행 오른쪽에 있고 선택 쿼리만 수정한다.
4. 정상 상태 하단은 숨기고 오류·읽기 전용·빈 목록·지원하지 않는 본문 안내는 유지한다.

### 추가 요구사항과 성공 기준

- **FR-024**: queryMap 루트 desc를 편집하고 위 동기화·보존·쓰기 제한을 적용해야 한다.
- **FR-025**: isNamed를 resultType과 같은 행 오른쪽에 배치해야 한다.
- **FR-026**: 하단 쿼리 개수를 제거하고 필요한 상태 안내만 표시해야 한다.
- **SC-011**: 위 네 인수 시나리오가 모두 통과한다.

### 화면 정리 명확화

desc는 queryMap 루트 속성으로 기존 query desc와 별개다. 빈 desc는 빈 문자열로 수정한다. 개수 제거는 하단 문구에 적용한다. 중요 미해결 사항은 없으며 기존 설명 표시 요구를 편집 입력으로 확장한다.

## 사용자 이야기 9 — 라벨과 Java 클래스 자동완성 (우선순위: P1)

사용자는 대문자로 시작하는 속성 라벨을 보고 ResultType에서 Java 클래스 후보를 선택한다.

### 명확화와 범위

UI 라벨만 Id, Desc, ResultType, IsNamed로 변경한다. XML 속성명은 기존대로 유지한다. 클래스 후보는 현재 프로젝트와 의존 라이브러리의 Java 클래스이며 선택하면 패키지를 포함한 이름을 저장한다. 직접 입력·빈 값·아직 존재하지 않는 클래스명도 허용한다. Java 지원을 활성화한 IDE를 대상으로 하며 인덱싱 중에는 IDE의 기본 완성 제한을 따른다. 중요 미해결 사항이 없어 추가 질문 없이 진행한다.

### 요구사항

- **FR-027**: 네 속성 라벨의 첫 글자를 대문자로 표시하고 기존 XML 속성명과 IsNamed 위치를 유지해야 한다.
- **FR-028**: ResultType에서 Java 클래스 후보 완성을 제공하고 선택한 클래스의 전체 이름을 선택 query의 resultType에 저장해야 한다. 입력 중 자동 제안과 Ctrl+Space 수동 호출은 IDE 완성 설정을 따른다.
- **FR-029**: 직접 입력과 비우기, 쿼리 전환, Source 동기화, 실행 취소·다시 실행·저장 및 잘못된 XML·읽기 전용 제한을 유지해야 한다. 편집기 해제 후 예약 작업이나 리스너가 원문을 변경하지 않아야 한다.

### 독립 검증 및 인수 시나리오

1. 네 라벨은 정확히 Id, Desc, ResultType, IsNamed이며 XML 속성명은 바뀌지 않는다.
2. 프로젝트의 서로 다른 패키지에 동명 클래스를 추가하고 ResultType에서 후보를 구분하여 선택하면 전체 이름이 선택 쿼리에 저장된다.
3. 직접 입력·빈 값·선택 전환·Source 갱신·실행 취소·다시 실행·저장이 정상 동작한다.
4. 잘못된 XML·읽기 전용에서는 수정이 제한되고 편집기 해제 시 자원을 해제한다.

**SC-012**: 위 네 시나리오와 기존 회귀 검증이 모두 통과한다.

## 사용자 이야기 10 — 파일 형식 아이콘 구분 (우선순위: P2)

사용자는 파일 목록과 편집 탭에서 쿼리 파일과 모델 파일을 색과 문자로 구분한다.

### 명확화

.glue_uml_ad는 연주황 원에 흰색 M, .glue_sql은 하늘색 원에 흰색 Q를 표시한다. 색은 각각 #F6B26B와 #87CEEB로 정한다. 밝은 테마와 어두운 테마에서 동일한 색과 글자를 사용하고 IDE 아이콘 배율을 따른다. 별도 질문이 필요한 미해결 사항은 없다.

### 요구사항과 인수 기준

- **FR-030**: .glue_uml_ad 파일 형식에 연주황 원과 흰색 M 아이콘을 제공해야 한다.
- **FR-031**: .glue_sql 파일 형식에 하늘색 원과 흰색 Q 아이콘을 제공해야 한다.
- **FR-032**: 아이콘은 설치 배포물에 포함되어야 하며 두 모듈 독립성·파일 형식 연결·XML 편집 및 기존 멀티뷰 기능을 유지해야 한다.

**독립 검증**: 두 파일 형식의 아이콘 리소스가 지정 색과 문자 도형을 갖는지 확인하고 배포물에 포함되는지 검사한다. 실제 IDE의 프로젝트 트리와 편집 탭에서도 각각 같은 아이콘이 보여야 한다.

**SC-013**: 두 아이콘이 지정 색과 문자로 구분되고 파일 형식 회귀 검증과 배포 빌드가 통과한다.

## 사용자 이야기 11 — 속성 입력 외형 통일 (우선순위: P1)

사용자는 통일된 입력란과 명확한 속성 라벨로 쿼리를 편집한다.

### 명확화

기존 Id 표시는 ID, Desc 표시는 Description으로 바꾸며 ResultType 표시는 유지한다. isNamed 체크박스의 화면 텍스트는 없애고 ResultType 오른쪽의 체크박스와 기능은 유지한다. 보조 기술을 위한 이름과 마우스 도움말은 유지한다. ResultType의 Java 클래스 자동완성은 유지하며 다른 문자열 입력과 테두리·배경·글꼴·높이를 맞춘다. XML 속성명은 바뀌지 않는다. 중요 미해결 사항이 없어 추가 질문 없이 진행한다. 이 요구는 기존 사용자 이야기 9의 표시 라벨 요구를 대체한다.

### 요구사항 및 인수 기준

- **FR-033**: 속성 라벨은 ID, Description, ResultType으로 표시하고 isNamed 체크박스에는 화면 텍스트를 표시하지 않아야 한다.
- **FR-034**: ResultType은 다른 문자열 입력과 같은 테두리·배경·글꼴·한 줄 높이를 사용해야 한다. Java 코드용 색상·검사 표시로 외형이 달라지지 않아야 하며 자동완성과 직접 입력은 유지해야 한다.
- **FR-035**: 체크박스의 위치·선택 동기화·XML 속성명과 기존 편집·저장·읽기 전용 처리를 유지해야 한다. 텍스트 없는 체크박스는 접근성 이름과 도움말로 식별할 수 있어야 한다.

**독립 검증**: 화면의 세 라벨과 무텍스트 체크박스를 확인하고 ResultType과 ID 입력의 스타일을 비교한다. 기존 클래스 후보 선택·전체 이름 저장·수정·동기화 회귀 검증을 실행한다.

**SC-014**: 세 표시 변경이 반영되고 입력 스타일 비교 및 기존 클래스 자동완성·편집 검증이 모두 통과한다.

## 사용자 이야기 12 — ResultType 실제 표시 보정 (우선순위: P1)

사용자는 ResultType의 텍스트가 세로 중앙에 있고 좌우 여백과 테두리 및 선명한 포커스 표시가 있는 입력란을 사용한다.

### 명확화

이전 스타일 일치 구현만으로 실제 표시가 같지 않다는 피드백을 반영한다. 텍스트 한 줄을 입력 높이의 세로 중앙에 놓고 좌우 내부 여백을 각각 기본 배율 6픽셀로 확보한다. 일반 테두리는 1픽셀, 포커스 시 테두리는 2픽셀로 표시하며 배율을 적용한다. 색상은 현재 IDE 테마의 입력 테두리·포커스 색상을 따른다. 이전 라벨·자동완성·XML 수정 동작을 유지한다. 추가 질문이 필요한 모호성은 없다.

### 요구사항과 인수 기준

- **FR-036**: ResultType의 텍스트 줄을 입력 영역의 세로 중앙에 배치하고 좌우 각각 6픽셀 이상의 여백을 확보해야 한다.
- **FR-037**: 일반 상태에 1픽셀 테두리, 포커스 상태에 2픽셀 테두리를 표시하고 포커스 변경에 따라 즉시 갱신해야 한다. 포커스 전후 입력 영역과 텍스트 위치는 유지해야 한다.
- **FR-038**: 테마와 배율을 반영하고 기존 클래스 자동완성·직접 입력·선택 동기화·실행 취소·저장·쓰기 제한을 유지해야 한다.

**독립 검증**: 실제 편집 컴포넌트를 배치·렌더링하여 중앙 정렬과 좌우 여백, 일반·포커스 테두리 차이를 확인한다. 스타일 속성 비교만으로 완료 처리하지 않는다.

**SC-015**: 렌더링 및 배치 검증과 기존 클래스 완성·편집 회귀 검증이 통과한다.

## 사용자 이야기 13 — ResultType 크기와 위치 미세 조정 (우선순위: P2)

ResultType 입력의 기존 높이를 2픽셀 줄이고 좌우 내부 패딩을 각각 1픽셀로 바꾸며 위치를 오른쪽으로 2픽셀 이동한다. 수치는 기본 배율 기준이며 IDE 배율을 적용한다. 패딩은 테두리 안쪽의 여백으로 해석하고 포커스 테두리 공간 2픽셀은 별도로 확보한다. 추가 질문이 필요한 모호성은 없다. 이 요구는 사용자 이야기 12의 좌우 6픽셀 여백 기준을 대체한다.

- **FR-039**: 기존 선호·최소 입력 높이를 기본 배율 2픽셀 줄이고 텍스트 세로 중앙 정렬을 유지해야 한다.
- **FR-040**: 좌우 내부 패딩을 각각 1픽셀로 적용하고 포커스 테두리와 텍스트가 겹치지 않아야 한다.
- **FR-041**: ResultType 입력만 기존 위치에서 오른쪽으로 2픽셀 이동하고 너비·라벨·체크박스 위치와 기존 자동완성·편집 기능을 유지해야 한다.

**독립 검증**: 기존 렌더링 및 배치 검증의 높이·패딩·그리드 오프셋 기준을 갱신하고 일반·포커스 이미지를 확인한다.

**SC-016**: 세 치수 변경과 기존 중앙 정렬·테두리·자동완성 회귀 검증이 통과한다.

## 사용자 이야기 14 — ResultType 왼쪽 패딩 (우선순위: P2)

ResultType 왼쪽 내부 패딩을 3픽셀로 조정한다. 기본 배율 기준이며 IDE 배율을 적용한다.

### 명확화

기존 테두리 공간 2픽셀 안쪽의 패딩으로 해석하여 왼쪽 전체 인셋은 5픽셀이다. 사용자 이야기 13의 왼쪽 1픽셀 패딩을 대체한다. 추가 질문이 필요한 모호성은 없다.

- **FR-042**: 왼쪽 내부 패딩을 3픽셀로 표시하고 일반·포커스 상태에 동일하게 적용해야 한다.
- **FR-043**: 오른쪽 패딩·높이·위치와 자동완성·편집 기능을 유지해야 한다.

**인수 검증**: 기존 배치 검증에서 왼쪽 전체 인셋 5픽셀, 오른쪽 3픽셀과 중앙 정렬을 확인하고 자동완성·편집 검증을 실행한다.

**SC-017**: 변경된 배치와 기존 자동완성·편집 검증이 통과한다.

## 사용자 이야기 15 — 입력 외형 일치 (우선순위: P1)

ResultType 입력의 왼쪽 위치·높이·텍스트 여백·테두리를 ID와 Description에 맞춘다. 이전 사용자 이야기 12~14의 개별 치수 기준은 이번 동일 외형 기준으로 대체한다.

### 명확화

기준은 실제 ID 입력 컴포넌트의 테마별 치수와 테두리다. ResultType 오른쪽의 체크박스와 Java 자동완성·편집 기능은 유지한다. 추가 질문은 필요하지 않다.

- **FR-044**: 세 입력의 왼쪽 경계·높이·텍스트 시작 여백을 동일하게 해야 한다.
- **FR-045**: IDE 테마의 기본 입력 테두리와 배율을 사용하고 자동완성·편집 기능을 유지해야 한다.
- **FR-046**: 테스트에서 세 입력을 함께 캡처하고 이미지를 직접 확인해야 한다.

**인수 기준**: 동일 문자열을 표시한 세 입력의 배치와 텍스트 시작 위치를 비교한다. 일반·포커스 상태를 캡처하고 기존 쿼리 테스트를 통과한다.

**SC-018**: 비교 캡처에서 세 입력이 정렬되고 쿼리 편집 회귀 검증이 통과한다.

## 사용자 이야기 16 — 어두운 테마의 실제 입력 여백 복구 (우선순위: P1)

사용자 캡처에서 ResultType 테두리와 여백이 소실되었다. 사용자 이야기 15의 ID·Description 기준 외형을 실제 IDE 어두운 테마에서도 보장한다.

### 명확화

단순히 테두리 객체를 공유하는 것으로는 충분하지 않다. 사용자가 보는 입력 외곽과 텍스트 여백을 기준으로 한다. ID와 동일한 높이·왼쪽 정렬·여백을 유지하며 자동완성·편집과 체크박스도 보존한다. 추가 질문이 필요한 사항은 없다.

- **FR-047**: 어두운 테마에서도 ResultType의 입력 테두리와 배경을 ID와 동일하게 표시해야 한다.
- **FR-048**: 실제 텍스트 시작 여백이 ID와 같고 0보다 커야 하며 높이와 왼쪽 정렬을 유지해야 한다.
- **FR-049**: 밝은 테마와 어두운 테마에서 세 입력을 함께 캡처하여 직접 확인하고 기존 자동완성·편집 검증을 통과해야 한다.

**인수 기준**: 같은 문자열을 표시한 세 입력의 경계·높이·텍스트 시작 위치와 테두리를 비교한다. 테마별 PNG에서 테두리와 내부 여백이 보이고 포커스 전환 후에도 내용 위치가 유지되어야 한다.

**SC-019**: 두 테마의 비교 캡처 및 기존 쿼리 회귀 검증을 통과한다.

## 사용자 이야기 17 — 안전한 문맥에서 쿼리 편집기 갱신 (우선순위: P1)

IDE가 Design 편집기를 생성할 때 Write-unsafe context 오류가 발생하지 않아야 한다. Source 최신 내용과 기존 편집 기능을 유지한다.

### 명확화

편집기 생성·탭 활성화·비활성화는 쓰기 안전 문맥이 아닐 수 있다. 이 생명주기 콜백에서는 문서 커밋이나 대기 편집 적용을 즉시 실행하지 않고 안전한 UI 실행으로 예약한다. 조회용 스냅샷은 PSI 커밋을 수행하지 않는다. 추가 질문이 필요한 사항은 없다.

- **FR-050**: 쓰기 안전성이 보장되지 않는 문맥에서도 Design 편집기 생성과 탭 전환이 오류 없이 완료되어야 한다.
- **FR-051**: 갱신은 올바른 modality를 지정한 안전한 실행에서 최신 Source를 반영하고 대기 편집·선택·실행 취소·읽기 전용 처리를 유지해야 한다.
- **FR-052**: 갱신 전에 편집기나 프로젝트가 폐기되면 예약 작업이 문서나 UI를 변경하지 않아야 한다.

**인수 기준**: 쓰기 비안전 문맥에서 미커밋 문서의 편집기 생성과 활성화를 실행하고 콜백 안에서는 커밋되지 않는지 확인한다. 이벤트 처리 후 최신 값이 표시되어야 한다. 예약 직후 폐기 시 오류·문서 변경이 없어야 한다.

**SC-020**: 해당 오류 재현 회귀 테스트와 기존 전체 편집 테스트가 모두 통과한다.

## 사용자 이야기 18 — 저장 시 SQL 앞뒤 공백 제거 (우선순위: P1)

.glue_sql 파일을 저장할 때 query SQL 본문 앞뒤의 공백·탭·줄바꿈을 제거한다. CDATA 바깥의 들여쓰기와 CDATA 안쪽의 앞뒤 줄바꿈을 모두 포함하며 SQL 내부 줄바꿈과 들여쓰기는 유지한다.

### 명확화

Source와 Design 중 어느 탭에서 편집했든 실제 파일 저장 직전에 적용한다. 정리된 본문은 기존 Design 편집과 동일한 CDATA 표현을 사용한다. 동일 id의 쿼리도 각각 처리하며 속성·네임스페이스·다른 XML 영역은 보존한다. 중첩 태그나 주석이 섞인 본문, 잘못된 XML, 읽기 전용 파일과 다른 파일 형식은 변경하지 않는다. 추가 질문이 필요한 사항은 없다.

- **FR-053**: 저장하는 .glue_sql의 단순 query 본문에서 SQL 앞뒤 공백을 제거하고 내부 공백·줄바꿈은 보존해야 한다.
- **FR-054**: Source·Design 저장에 동일하게 적용하고 중복 id·속성·XML 구조·CDATA 종료 문자열을 안전하게 보존해야 한다.
- **FR-055**: 대상 밖 파일과 복합 본문·잘못된 XML·읽기 전용 문서는 보존하고, 반복 저장은 추가 변경을 만들지 않으며 실행 취소와 화면 동기화를 유지해야 한다.

**인수 기준**: 사용자가 제시한 CDATA 바깥·안쪽 공백 예시를 저장하여 두 본문이 같은 SQL이 되는지 확인한다. 디스크 내용·내부 줄바꿈·중복 id·Source와 Design 동기화·실행 취소·보호 대상 보존을 검증한다.

**SC-021**: 저장 정리 회귀 검증과 기존 전체 테스트 및 배포 빌드가 통과한다.

## 사용자 이야기 19 — 파일을 열 때 SQL 공백 정리 (우선순위: P1)

.glue_sql 파일을 열 때도 저장 시와 같은 query SQL 앞뒤 공백 정리를 적용한다.

### 명확화

실제 파일 열기 이벤트에서 문서를 정리하며 디스크 반영은 기존 저장 시점에 수행한다. 열기만으로 문서가 변경되면 미저장 상태가 된다. Source·Design은 같은 문서를 사용하며 기존 내부 공백·XML 보존·제외 규칙과 실행 취소를 유지한다. 쓰기 비안전 열기 문맥에서는 즉시 변경하지 않고 안전한 실행으로 예약한다. 추가 질문은 필요하지 않다.

- **FR-056**: 파일을 열면 저장 정리와 동일한 SQL 앞뒤 공백 제거 결과를 Source와 Design에 표시해야 한다.
- **FR-057**: 열기 작업에서 쓰기 안전 문맥을 사용하고 처리 전에 파일이 닫히거나 프로젝트가 폐기되면 문서를 변경하지 않아야 한다.
- **FR-058**: 기존 제외 규칙과 저장·실행 취소·반복 처리 안전성을 유지하고 정리 결과는 저장 전까지 문서에만 반영해야 한다.

**인수 기준**: 실제 파일 열기로 사용자 예시의 SQL이 정리되고 두 화면이 같은 값을 보이는지 확인한다. 저장 전 디스크 원본 보존과 미저장 상태·실행 취소·반복 열기·쓰기 비안전 이벤트·닫힌 파일·제외 대상 보존을 검증한다.

**SC-022**: 파일 열기 회귀 검증과 기존 전체 테스트 및 배포 빌드가 통과한다.

## 사용자 이야기 20 — SQL 색상과 키워드 완성 (우선순위: P1)

Design의 SQL 입력에서 키워드·숫자·따옴표 토큰을 색으로 구별하고 SQL 키워드를 자동완성한다. 기존 문법 기능 제외 범위는 이번 요구에 한해 변경한다.

### 명확화

DBeaver의 공통 SQL 예약어·확장 키워드·실행 및 DDL 키워드 목록을 기준으로 하고 특정 DB 전용 키워드·스키마·테이블·열 후보는 포함하지 않는다. 키워드는 대소문자와 관계없이 주황색, 정수·소수·지수 숫자는 파란색, 작은따옴표와 큰따옴표로 감싼 토큰은 녹색으로 표시한다. 주석 안의 단어·숫자·따옴표는 별도 토큰으로 강조하지 않는다. 따옴표 반복 이스케이프와 미완성 따옴표를 처리한다.

키워드 완성은 입력 중 IDE 자동 팝업 설정 및 Ctrl+Space를 따르며 대소문자를 구분하지 않고 접두어로 찾는다. 문자열·주석·숫자 안에서는 후보를 제시하지 않는다. SQL 문법 오류 진단·실행은 범위 밖이고 Source의 XML 구문 표시와 ResultType의 Java 클래스 완성은 유지한다. 추가 질문이 필요한 모호성은 없다.

- **FR-059**: DBeaver 공통 목록의 SQL 키워드를 식별자 일부와 구별하여 대소문자와 관계없이 주황색으로 표시해야 한다.
- **FR-060**: 숫자는 파란색, 작은따옴표·큰따옴표 토큰은 녹색으로 표시하고 문자열·주석 내부를 잘못 분리하지 않아야 한다.
- **FR-061**: 동일한 키워드 목록으로 접두어 자동완성을 제공하고 선택한 후보를 현재 SQL 입력에 삽입해야 한다.
- **FR-062**: 문자열·주석·숫자·읽기 전용 입력에서 키워드 후보를 제시하지 않고 다른 입력란의 완성을 방해하지 않아야 한다.
- **FR-063**: 쿼리 선택·Source 동기화·실행 취소·열기 및 저장 정리 후에도 강조와 완성을 유지하고 SQL 원문을 구문 표시 때문에 변경하지 않아야 한다.
- **FR-064**: 밝은 테마와 어두운 테마에서 지정한 색상 계열이 식별 가능해야 하며 테스트 캡처로 직접 확인해야 한다.

**인수 기준**: 혼합 대소문자 키워드·숫자·따옴표 이스케이프·미완성 문자열·주석·식별자의 토큰 경계를 검사한다. 실제 완성 후보 선택이 선택 쿼리에만 반영되고 실행 취소로 복구되는지 검증한다. 두 테마의 실제 편집 컴포넌트를 캡처하여 색상을 확인한다.

**SC-023**: 토큰·완성·상태 유지·테마 캡처 검증과 기존 전체 테스트 및 배포 빌드가 통과한다.

## 사용자 이야기 21 — SQL 파라미터 색상과 편집 여백 (우선순위: P1)

이름 있는 SQL 파라미터를 구분하고 쿼리 목록과 줄 번호의 가독성을 개선한다.

### 명확화

:parameter 형태는 콜론과 이름을 하나의 토큰으로 cyan 계열로 표시한다. 문자열·주석 안의 같은 형태는 기존 색상을 유지하고 PostgreSQL 형 변환 ::type은 파라미터로 인식하지 않는다. 파라미터 내부에는 키워드 완성을 제공하지 않는다. 쿼리 ID 목록은 각 셀 좌우에 기본 배율 8픽셀 여백을 더하고 선택 배경·포커스 표시를 유지한다. 줄 번호 뒤의 여백도 기본 배율 8픽셀을 추가하며 IDE 배율과 편집기 수명을 따른다. 별도 질문이 필요한 모호성은 없다.

- **FR-065**: SQL의 이름 있는 파라미터 전체를 cyan으로 표시하되 문자열·주석·형 변환과 구별하고 키워드 완성을 제외해야 한다.
- **FR-066**: 쿼리 ID 목록 셀 좌우에 각각 배율 적용 8픽셀 여백을 추가하고 선택·표시 기능을 유지해야 한다.
- **FR-067**: 줄 번호 영역 오른쪽에 배율 적용 최소 8픽셀 빈 공간을 확보하고 편집기 교체·해제에도 유지되어야 한다.

**SC-024**: 실제 토큰·셀 렌더링·줄 번호 영역 검증과 밝은/어두운 테마 캡처에서 세 표시 변경을 확인한다.

## 사용자 이야기 22 — 다중 DataSource 설정 (우선순위: P1)

Settings에 GlueFramework 상위 메뉴와 GlueQueryEditor 하위 메뉴를 제공하고 여러 DataSource 등록 정보를 관리한다.

### 명확화

사용자 선택으로 프로젝트별 관리를 확정했다. 등록 항목은 안정적인 ID, 이름, JDBC URL, 선택적 드라이버 클래스·사용자명·비밀번호다. 여러 항목을 추가·수정·삭제하고 Apply/OK로 저장하거나 Cancel/Reset으로 미적용 변경을 버릴 수 있다. 이름과 JDBC URL은 필수이며 중복 이름을 허용하지 않는다. 실제 DB 연결·연결 테스트·SQL 실행·드라이버 내려받기는 이번 범위에 포함하지 않는다.

비밀번호를 입력하지 않으면 기존 저장 값을 유지하고 별도 삭제 옵션을 제공한다. 비밀번호는 IDE 보안 저장소에 보관하고 일반 설정 XML에는 포함하지 않는다. 삭제된 DataSource의 저장 비밀번호도 삭제한다. 보안 저장소 작업은 UI 스레드 밖에서 실행하고 실패하면 설정 적용 오류를 표시한다.

- **FR-068**: Settings의 GlueFramework > GlueQueryEditor에서 DataSource 목록과 접속 정보 편집 화면을 제공해야 한다.
- **FR-069**: 여러 DataSource를 추가·수정·삭제하고 프로젝트 설정에 저장하여 다음 설정 열기와 상태 재로딩 후에도 복원해야 한다.
- **FR-070**: 필수 이름·JDBC URL과 이름 중복을 검증하고 Apply·Reset·Cancel의 표준 의미를 유지해야 한다.
- **FR-071**: 비밀번호를 일반 설정과 분리하여 보안 저장소에서 유지·변경·삭제하고 UI 스레드에서 저장소를 호출하지 않아야 한다.
- **FR-072**: SQL 강조·완성·Source 동기화·열기/저장 정리·읽기 전용과 기존 편집 동작을 유지해야 한다.

**SC-025**: 설정 트리 등록·다중 항목 CRUD·검증·상태 직렬화·비밀번호 분리·취소·설정 화면 캡처와 기존 전체 테스트 및 배포 빌드가 통과한다.
## 사용자 이야기 23 — DB 메타데이터 자동완성과 설정 개선 (우선순위: P1)

### 명확화와 이전 범위 갱신

이번 요청은 이야기 22의 DB 연결 제외를 메타데이터 조회에 한해 확장한다. SQL 실행은 계속 제외한다. 줄 번호 여백은 기존 8픽셀 예약에서 10픽셀을 더한 18픽셀로 늘린다. Settings의 목록/폼 사이 드래그 구분선을 제거하고 목록 너비는 고정한다.

사용자는 로컬 JDBC JAR 지정을 기본으로 하고 자동 다운로드 버튼도 제공하도록 답했다. Oracle, MySQL, MariaDB, PostgreSQL, Impala 중 하나를 선택한다. DB 기본 드라이버 클래스를 제공하되 사용자 수정과 복수 로컬 JAR 지정을 허용한다. 공개 배포 주소가 있는 네 DB는 기본 다운로드 주소를 제공하고 Impala는 공급자에게서 받은 직접 HTTPS JAR/ZIP 주소를 입력하여 같은 버튼으로 받는다. 다운로드 실패 시 기존 JAR 설정은 유지한다.

에디터에서 프로젝트 DataSource 하나를 선택하고 메타데이터 새로고침을 명시적으로 요청한다. 선택은 프로젝트별로 유지한다. 조회 가능한 테이블과 각 테이블의 컬럼 이름을 읽고 테이블별 관계와 전체 Distinct 이름 목록을 메모리에 보관한다. 구별은 원문 이름의 정확한 일치 기준으로 하며 검색은 대소문자 무시 접두어다. 다른 DataSource의 후보는 섞지 않는다. 선택하지 않거나 조회 전에는 기존 키워드 완성을 제공한다. 설정 변경·삭제 시 해당 캐시를 무효화한다. 자동완성 자체는 DB에 접속하지 않는다.

- **FR-073**: 줄 번호 오른쪽 예약 여백을 배율 적용 18픽셀로 늘려야 한다.
- **FR-074**: DataSource 설정의 가운데 크기 조절 구분선을 제거하고 다섯 DB 종류를 선택·저장·복원해야 한다. 기존 항목은 JDBC URL로 종류를 유추하며 불명확하면 Oracle을 기본으로 한다.
- **FR-075**: 로컬 JDBC JAR 복수 지정과 선택 DB 기본 드라이버 클래스를 제공하고 자동 다운로드 버튼으로 HTTPS JAR/ZIP을 받아 초안에 반영해야 한다. 다운로드·조회는 UI 스레드를 막지 않아야 하며 실패·취소 시 기존 상태를 유지해야 한다.
- **FR-076**: 프로젝트에서 선택한 DataSource의 테이블·각 컬럼 정보를 JDBC 메타데이터로 읽고 중복 없는 이름 목록으로 관리하며 조회 리소스를 해제해야 한다.
- **FR-077**: SQL 완성에 선택한 DB의 테이블·컬럼 이름과 종류를 키워드와 함께 제공하고 동일 이름의 후보를 중복 표시하지 않아야 한다. 문자열·주석·파라미터·읽기 전용 제외 규칙은 유지해야 한다.
- **FR-078**: 메타데이터 조회는 진행 상태·취소·안전한 오류를 제공하고 실패한 조회는 직전 성공 캐시를 보존해야 한다. 설정 변경·삭제·빠른 전환 시 오래된 결과가 현재 DB에 반영되지 않아야 한다. 비밀번호는 보안 저장소에서 배경 조회하고 오류에 접속 정보·비밀번호를 노출하지 않아야 한다.

**인수 시나리오**: 다섯 종류를 각각 선택·저장·복원한다. 중복 테이블/컬럼 응답에서 관계 및 Distinct 목록을 검사한다. DB 전환·설정 변경·실패·취소에서 캐시가 격리되는지 확인한다. 실제 SQL 완성 후보 선택이 XML에 반영되는지 검증한다. 다운로드 성공·잘못된 JAR/ZIP·실패와 리소스 해제를 검사한다. 실제 설정 및 여백 컴포넌트를 캡처한다.

**SC-026**: DB 종류·드라이버 다운로드·메타데이터·캐시·실제 자동완성·캡처와 기존 전체 테스트 및 배포 빌드가 통과한다. 다섯 실제 DB 서버에 대한 접속 확인은 이용 가능한 서버가 있을 때 별도 기록한다.
